# SDD 文档体系（Spec-Driven Development）

> 本目录是项目从 **Vibe Coding（快速验证）** 切换到 **SDD（规范驱动开发）** 后的"单一事实源"。
> 任何代码改动、新模块、UI 重构、接真后端，都必须能从这套文档里追溯到"为什么这么做"。

---

## 1. 为什么需要 SDD

| 维度 | Vibe Coding 阶段（已结束） | SDD 阶段（当前） |
|------|---------------------------|-----------------|
| 目标 | 验证产品 idea，3 秒出原型 | 长期维护、跨人协作、可追溯迭代 |
| 决策 | 在编辑器里直觉式拍板 | 文档先行，代码是文档的产物 |
| 文档 | 事后补、零散、易过期 | 事前写，作为 PR 唯一依据 |
| 风险 | 改动随机，回归无主 | 每个改动绑定 spec/plan 条目 |

**判断 SDD 是否生效的硬指标**：

- 任何一个 PR 都能在 `spec.md` / `plan.md` / `tasks.md` 里找到对应条目；
- 新成员只读这四份文档（不看代码）就能在 1 小时内说出系统骨架；
- 出现争议时，先改文档再改代码，而不是相反。

## 2. 文档分层（六件套）

按"先 What → 再 How → 再 Test → 后 Do"的顺序读：

```
constitution.md   永恒原则 — 改它需要团队评审
        │
        ├──────────────────────────────────────┐
        ▼                                      ▼
prd.md            产品需求 — 用户故事 / 优先级 / 版本路线（鲜活）
        │
        ▼
spec.md           产品规范 — WHAT / WHY，业务契约（稳定）
        │
        ▼
plan.md           技术方案 — HOW，工程语言（核心交付物）⭐
        │
        ├──────────────────────────────────────┐
        ▼                                      ▼
test.md           测试策略 — 金字塔 / 工具链 / 覆盖率 / E2E 旅程
        │
        ▼
tasks.md          当前迭代任务 — DO，可执行清单
```

| 文件 | 角色 | 更新频率 | 唯一负责人 |
|------|------|---------|-----------|
| [`constitution.md`](./constitution.md) | 项目宪法、不变原则、技术红线 | 季度级 | 技术负责人 |
| [`prd.md`](./prd.md) | 用户画像、用户故事、RICE、版本路线 | 迭代级 | 产品 |
| [`spec.md`](./spec.md) | 业务规范契约、用例编号、状态机 | 版本级 | 产品 + 业务 |
| [`plan.md`](./plan.md) | 架构、模块、数据流、迭代路线、ADR | 迭代级（双周） | 技术负责人 |
| [`test.md`](./test.md) | 测试金字塔、工具链、覆盖率、E2E 主旅程 | 季度级 | 测试 / 全员 |
| [`tasks.md`](./tasks.md) | 本迭代可执行任务、负责人、验收 | 每日 | 全员 |

### 2.1 prd.md 与 spec.md 的边界

- **prd.md** = "我们在思考要做什么 / 怎么做"（鲜活、变化快、有 RICE 优先级、有需求池）
- **spec.md** = "我们已经承诺并实现了什么"（稳定、是工程契约、有用例编号供 PR 引用）

新需求先进 prd 评估 → 决策做 → 沉淀到 spec → 进入 plan 拆任务。

## 3. 与已有文档的关系

本项目原先已有三份偏 UI 的文档，它们**不被废弃**，而是被 SDD 体系**收编**：

| 既有文档 | SDD 中的位置 |
|---------|-------------|
| `docs/BUSINESS-DESIGN.md` | 被 `spec.md` 引用为业务状态机权威源 |
| `docs/UI_DESIGN_SPEC.md` | 被 `plan.md` 引用为前端表现层规范 |
| `docs/UNIFIED_VISUAL_MASTERPLAN.md` | 被 `plan.md` 引用为视觉收敛执行依据 |
| `docs/UI_REFACTOR_TASK_LIST.md` | 被 `tasks.md` 吸收（已完成项归档） |

> 原则：**业务/视觉细节留在原文档，SDD 文档只负责"指针 + 决策"**，避免重复维护。

## 4. 工作流（强制）

### 4.1 新增功能

```
1. 在 spec.md 增加用例（WHAT），并标注业务价值（WHY）
2. 在 plan.md 增加技术决策（HOW），含影响的模块、数据流、风险
3. 在 tasks.md 拆出任务，关联 spec 条目编号
4. 提 PR，PR 描述里贴出 [spec-XX][plan-YY] 编号
5. CR 时只检查"是否符合 plan"，不再讨论方案
```

### 4.2 修复 Bug

```
1. 在 tasks.md 登记一条 bug，关联到 spec 的哪条用例失效
2. 如 bug 暴露 plan 漏洞 → 同步修订 plan.md
3. 如 bug 暴露 spec 漏洞 → 升级到产品讨论
```

### 4.3 重构

```
1. 在 plan.md 找到要重构的模块章节
2. 写出"现状 → 目标 → 迁移步骤"，作为 ADR（架构决策记录）追加到 plan.md 末尾
3. 拆 tasks，分多次小 PR 推进（禁止"大爆炸式"重构）
```

---

## 5. 文档质量红线

- **可执行**：plan.md 里的每个决策必须能落到具体文件路径
- **可验证**：spec.md 里的每条用例必须有验收标准
- **可追溯**：tasks.md 里的每个任务必须能链接到 spec/plan 条目
- **不臆想**：禁止描述"未来某天可能加的功能"，未确认的需求只写在 ADR 草案区

## 6. 起步阅读顺序

第一次看本仓库，按以下顺序 45 分钟内读完即可上手：

| 步骤 | 文件 | 关注什么 | 时长 |
|------|------|---------|------|
| 1 | 本文件 | SDD 是什么、为什么 | 5 分钟 |
| 2 | [`constitution.md`](./constitution.md) | 哪些事**绝对不能做** | 5 分钟 |
| 3 | [`prd.md`](./prd.md) | 我们的用户是谁、痛点是什么 | 10 分钟 |
| 4 | [`spec.md`](./spec.md) | **做了什么**、用例契约 | 10 分钟 |
| 5 | [`plan.md`](./plan.md) | **怎么做** ⭐ 核心 ⭐ | 10 分钟 |
| 6 | [`test.md`](./test.md) | 测试金字塔与覆盖目标 | 5 分钟 |
| 7 | [`tasks.md`](./tasks.md) | 当前要做什么 | 按需 |
