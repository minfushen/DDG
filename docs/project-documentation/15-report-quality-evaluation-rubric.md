# 15 报告质量评测 Rubric 与回归闭环

本文档定义智能尽调报告的质量评测标准，用于把“报告像不像客户经理能用”从主观体验转化为可复测、可回归、可持续优化的工程闭环。

## 目标

当前系统已经具备 DeepResearch 计划生成、证据采集、正文级 Evidence 引用、HITL、报告装配和工具调用脱敏可观测能力。下一阶段的关键不是继续堆工具，而是建立稳定的报告质量评测机制：

- 每次跑完一家企业，都能自动判断报告是否达到 MVP 可演示标准。
- 每次修改财务、行业、工商、司法、报告合成逻辑，都能用同一批公司回归测试。
- 每个失败点都能明确指向修复动作，而不是靠肉眼泛泛判断“报告不专业”。

## 评测对象

评测器输入为报告 JSON，优先支持 DeepResearch 报告结构：

- `enterprise_name`
- `risk_score` / `risk_rating`
- `credit_decision`
- `report_chapters`
- `evidence` / `evidence_docs`
- `claims`
- `gaps`
- `tool_traces`

评测器实现文件：

- `backend/app/agents/research_engine/report_quality_evaluator.py`

## 总分与通过标准

总分 100 分，按维度加权。

| 维度 | 权重 | 关注点 |
| --- | ---: | --- |
| 主体识别 | 10 | 企业名称是否被正确识别，是否混入“分析一下”等任务话术 |
| 报告结构 | 10 | 是否稳定输出 8 章贷前尽调结构 |
| 证据深度 | 15 | evidence 数量、高可信证据、可点击来源链接 |
| 正文级引用 | 15 | 关键结论是否绑定 evidence_refs，引用 ID 是否有效 |
| 财务分析深度 | 15 | 是否覆盖近三年收入、利润、现金流、资产负债、财务异常信号 |
| 行业分析深度 | 15 | 是否覆盖行业定位、周期、竞争格局、政策、上下游、授信关注点 |
| 工商/司法覆盖 | 8 | 是否覆盖工商登记、经营范围、股权、裁判、执行、处罚等 |
| 授信建议一致性 | 7 | 分数、风险等级、准入建议、额度期限担保条件是否一致 |
| 语言质量 | 5 | 是否存在占位、mock、病句、串场、明显错词 |

通过标准：

- 总分 `>= 75`
- 不存在 `P0` 阻断问题
- `P1` 高优先级问题不超过 3 个

建议演示标准：

- 总分 `>= 80`
- 财务分析深度 `>= 75`
- 行业分析深度 `>= 75`
- 正文级引用 `>= 80`

## 问题等级

| 等级 | 含义 | 示例 | 处理策略 |
| --- | --- | --- | --- |
| P0 | 阻断演示或严重误导 | 企业主体被识别成“分析一下士兰微”；正文没有任何 evidence 引用 | 必须修复后再演示 |
| P1 | 明显影响可信度 | 财务章节大量“暂不可用”；行业错分；高可信证据不足 | 当前迭代优先修复 |
| P2 | 体验或完整性问题 | 可点击来源少；某章节内容偏薄；信贷条件不够细 | 进入后续优化 |

## 8 章报告结构验收

报告必须稳定输出以下章节：

1. 报告摘要与授信建议
2. 企业主体与治理结构
3. 财务状况与偿债能力
4. 行业与经营环境
5. 司法与合规风险
6. 交叉验证与重大风险
7. 信贷方案建议
8. 证据链与待补充材料

每章至少应包含：

- `summary`、`findings` 或 `subsections` 中任意一种正文内容。
- 除证据附录外，关键章节应尽量包含 `evidence_refs` 或 `summary_citations`。

## 财务章节质量要求

财务章节不应只拼指标，而要形成诊断。最低要求：

- 明确近三年口径。
- 覆盖营业收入、净利润、毛利率、经营现金流、资产负债率、流动比率、应收账款等关键指标。
- 对财报增强尽调，优先输出近三年财务驾驶舱，至少覆盖收入利润、盈利能力、杠杆水平、短期偿债、现金流结构和营运资金占用。
- 对至少一个异常信号形成“现象与归因、风险定性、核查要点”。
- 财务结论绑定结构化财报、公告或财务诊断 evidence。
- 避免“财务专项报告待补充”“暂不可计算”大量堆叠。

典型 P1 问题：

- 上市公司却没有近三年财务分析。
- 只有最近一年指标，没有趋势判断。
- 有三年财务数据但没有趋势图表或核心财务数据表。
- 财务结论没有 evidence_refs。
- 文案出现“销售额为净利润”“资产持有率”等不专业表达。

## 行业章节质量要求

行业章节必须从“行业科普”升级为“尽调诊断”。最低要求：

- 明确细分行业定位，而不是泛泛写“制造业”“贸易/进出口”。
- 覆盖行业周期、竞争格局、政策环境、上下游议价能力、授信关注点。
- 对上市公司应尽量结合主营构成、年报经营讨论、公告线索或行业知识库。
- 行业结论绑定 evidence。

典型 P1 问题：

- 半导体公司被识别成贸易/进出口。
- 行业章节只有“竞争激烈、政策利好”等通用话术。
- 没有同业、周期、上下游、授信关注点。

## 证据与正文级引用要求

报告不能只在附录堆 evidence。关键结论旁必须能看到“这句话由哪些证据支撑”。

最低要求：

- 完整尽调建议至少 16 项 evidence。
- 至少 4 项高可信 evidence。
- 至少 4 项 evidence 有 `source_url`。
- 至少 5 个非附录章节包含正文级引用。
- 所有 `evidence_refs` 必须能在 evidence 列表中找到对应 ID。

## 授信建议一致性要求

授信建议必须与风险分、风险等级、证据缺口一致：

- 低分报告不能给出明显积极准入建议。
- 高风险章节应反映到额度、期限、担保、提款前置条件和贷后监控。
- 不能出现“准入建议：建议采纳”“建议可口”等明显病句。

## 语言质量红线

以下表达进入正式报告会触发扣分：

- `暂不可用`、`暂不可计算` 大量堆叠
- `报告专项待补充`、`专项报告待补充`
- `模拟数据`、`mock`、`兜底模拟`
- `牛奶准入`、`建议可口`、`边界边界`
- `状况与偿债能力`、`回周期`

## 使用方式

评测一个报告 JSON：

```bash
cd backend
./venv312/bin/python -m app.agents.research_engine.report_quality_evaluator /path/to/report.json --pretty
```

带回归样例评测：

```bash
cd backend
./venv312/bin/python -m app.agents.research_engine.report_quality_evaluator \
  /path/to/report.json \
  --sample regression_samples/listed_companies/silan_micro.json \
  --pretty
```

输出字段：

- `overall_score`：总分
- `grade`：A/B/C/D/E
- `passed`：是否达到当前 MVP 通过标准
- `dimension_scores`：各维度得分
- `issues`：P0/P1/P2 问题列表
- `metrics`：章节数、证据数、引用数、占位表达数等
- `recommendations`：优先修复建议

## 离线批量回归

离线批量脚本用于评测已经生成好的报告 JSON，不会创建任务，也不会调用外部数据源。

脚本位置：

- `backend/scripts/run_report_quality_regression.py`

默认输入目录：

- `backend/output/reports`

报告生成完成后，后端会自动把任务报告保存到该目录，文件名格式为：

```text
<task_id>_<enterprise_name>_report.json
```

例如：

```text
2026061322210282240263_药明康德_report.json
```

默认输出目录：

- `backend/regression_runs/<timestamp>/`

运行命令：

```bash
cd backend
./venv312/bin/python scripts/run_report_quality_regression.py
```

指定报告目录：

```bash
cd backend
./venv312/bin/python scripts/run_report_quality_regression.py \
  --input-dir /path/to/report-json-dir \
  --run-id manual_regression_001
```

输出文件：

- `summary.json`：结构化汇总，适合后续接 CI 或前端调试页。
- `summary.md`：人工可读汇总，包含每家公司分数、通过状态、P0/P1/P2 数量和 Top Issue。
- `reports/*.json`：匹配到的报告副本。
- `evaluations/*.quality.json`：每家公司完整评测结果。

匹配逻辑：

1. 优先按样例 `sample_id` 匹配文件名。
2. 其次按股票代码匹配。
3. 再按公司简称、公司全称和别名匹配报告内容。

如果某家公司没有找到对应报告，汇总中会标记为 `missing_report`，并生成 P0 问题，提示先保存报告 JSON 后再回归。

- 加一个批量评测脚本，定期跑 10 家公司并生成 Markdown 总结。
