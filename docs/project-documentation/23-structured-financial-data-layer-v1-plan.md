# 23 Structured Financial Data Layer v1 实施计划

## 背景

当前 DDG-Agent 财务分析、交叉验证和行业分析的主要问题不是“没有模型写作能力”，而是输入数据和证据上下文不稳定：

- AKShare、东方财富等结构化源已能提供财务数据，但字段、单位、期间、口径和来源置信度没有形成统一消费层。
- 财务 writer 仍容易拿散乱指标生成文本，导致表达机械、术语异常、口径混乱。
- 财务图表和二维表展示已具备雏形，但数据源、单位转换、趋势描述和关键指标覆盖仍需稳定。
- 巨潮年报 PDF、交易所公告 PDF、网页公告、新闻和研报摘要尚未形成可进入 Evidence/RAG/报告的处理闭环。

因此下一阶段不先做完整 Document Intelligence Pipeline，而是先落地 Structured Financial Data Layer v1，用结构化数据源快速提升财务分析质量，再把 PDF/公告/网页资料闭环接入财务交叉验证和行业分析。

## 总体路线

```text
Structured Financial Data Layer v1
-> 财务诊断 Writer 重构
-> 财务九宫格和表格展示优化
-> 巨潮年报 PDF / 交易所公告 PDF / 网页公告新闻研报摘要处理闭环
-> Document Intelligence Pipeline v1
```

## v1 目标

### 1. 结构化财务数据统一包

将 AKShare、东方财富和后续巨潮结构化结果统一为 `FinancialStatementPackage`。

核心要求：

- 计算层统一使用“元”。
- 展示层统一自动转换为“亿元/万元/%/倍/天”。
- 明确期间类型：年报、中报、三季报、单季、TTM。
- 明确报表口径：合并报表、母公司报表、归母、扣非。
- 每个字段保留来源、置信度、期间、单位和 evidence refs。

建议 schema：

```json
{
  "company_name": "三安光电",
  "stock_code": "600703",
  "periods": ["2022", "2023", "2024"],
  "period_type": "annual",
  "unit_base": "yuan",
  "statements": {
    "income_statement": {},
    "balance_sheet": {},
    "cashflow_statement": {}
  },
  "metrics": {},
  "trends": {},
  "cross_source_validation": {},
  "red_flags": [],
  "evidence_refs": [],
  "data_boundary": []
}
```

### 2. 关键字段覆盖

第一阶段必须稳定输出以下字段：

| 类别 | 字段 |
| --- | --- |
| 收入利润 | 营业收入、营业成本、毛利率、营业利润、归母净利润、扣非净利润 |
| 现金流 | 经营活动现金流净额、投资活动现金流净额、筹资活动现金流净额、收入现金含量 |
| 资产负债 | 总资产、总负债、资产负债率、货币资金、短期借款、有息负债、应收账款、存货 |
| 偿债 | 流动比率、速动比率、现金短债比、EBITDA、EBITDA 利息保障倍数 |
| 营运效率 | 应收账款周转天数、存货周转天数、总资产周转率 |
| 盈利质量 | ROA、ROE、销售净利率、扣非利润趋势、非经常性损益依赖 |

### 3. 跨源校验

AKShare 和东方财富都返回结构化数据，因此不需要文档解析，但需要字段级交叉校验。

规则：

- 同一字段同一期间差异小于阈值：标记 `verified`。
- 差异超过阈值：生成 `evidence_gap`，报告中提示需人工复核。
- 一方缺失、一方存在：保留可用值，但标记 `single_source`。
- 两方都缺失：进入 `data_boundary` 和待补充资料清单。

建议阈值：

- 金额类：相对差异 > 1% 且绝对差异 > 100 万，进入复核。
- 比率类：差异 > 0.5pct，进入复核。
- 日期/期间/口径不一致：直接进入复核。

### 4. 财务诊断 Writer 重构

LLM 或模板 writer 不再直接吃散乱字段，而是消费 `FinancialStatementPackage`。

输出结构固定为：

1. 收入与利润分析。
2. 资产负债分析。
3. 盈利质量与营运效率。
4. 偿债能力与财务信号异常。
5. 数据边界与核查动作。

文本要求：

- 必须使用近三年数据对比。
- 必须说明趋势，而不是只报最新值。
- 必须区分净利润和扣非净利润。
- 必须解释利润和经营现金流差异。
- 必须把重资产、折旧摊销、资产减值、政府补助、产能利用率等行业解释作为可选上下文。
- 禁止输出“最新原来”“鱼子”等错误词。
- 禁止使用未经结构化包提供的数字。

### 5. 财务九宫格和表格展示优化

后端输出稳定 `financial_dashboard`，前端只负责渲染。

九宫格建议：

1. 营业收入趋势。
2. 营业成本与毛利率。
3. 归母净利润与扣非净利润。
4. 经营现金流净额。
5. 资产负债率。
6. 货币资金与短期借款。
7. 应收账款与周转天数。
8. 存货与周转天数。
9. ROE / ROA / EBITDA 利息保障倍数。

二维表要求：

- 金额展示自适应亿元/万元。
- 表头明确年份和单位。
- 行列分割线清晰。
- 增加“波动趋势”列。
- 指标名称使用标准中文，不出现 EBITDA 误译或 ROE 被错误翻译。

## 第二阶段：公告/PDF/网页资料处理闭环

Structured Financial Data Layer 解决结构化财务指标问题，但财务分析、交叉验证和行业分析还需要公告、年报经营讨论、交易所问询、重大诉讼、行业新闻和研报摘要支撑。

第二阶段处理对象：

| 资料 | 主要用途 |
| --- | --- |
| 巨潮年报 PDF | 年报经营讨论、主营构成、审计意见、附注、非经常性损益、重大风险 |
| 交易所公告 PDF | 监管问询、重大诉讼、担保质押、资产减值、关联交易 |
| 网页公告 | 公司公告、监管公告、行业协会发布信息 |
| 新闻舆情 | 重大经营事件、处罚、产能、价格、客户变化 |
| 研报摘要 | 行业周期、竞争格局、同业指标、经营解释假设 |

最小闭环：

```text
公告/PDF/网页搜索命中
-> 正文读取 / PDF 文本抽取
-> block 化和来源定位
-> 字段/主题抽取
-> Evidence 生成
-> 财务交叉验证 / 行业诊断 / 报告正文引用
```

优先抽取主题：

- 年报经营讨论中的收入增长来源、毛利率变化原因、产能利用率、折旧摊销、政府补助。
- 主营构成和产品/区域/客户结构。
- 资产减值、存货跌价、商誉减值、应收坏账。
- 监管问询、重大诉讼、行政处罚、担保质押。
- 行业价格周期、供需变化、政策变化、同业扩产。

## 与 Document Intelligence Pipeline 的关系

Document Intelligence Pipeline 仍然重要，但不是本轮第一优先级。

当前顺序：

1. 结构化财务数据源已经可用，先做标准化、校验和诊断写作。
2. 巨潮年报 PDF、交易所公告 PDF、网页公告和研报摘要进入轻量资料处理闭环。
3. 当上传审计报告、扫描件、复杂 Excel、多格式客户资料成为主要输入时，再完整落地 Document Intelligence Pipeline v1。

## 验收标准

### 财务数据层

- 同一公司 AKShare/东方财富字段可统一到同一 schema。
- 金额统一用元计算，报告展示自动转亿元。
- 至少覆盖三年收入、成本、净利润、扣非、经营现金流、资产负债率、应收、存货、短期借款。
- 跨源差异能生成 evidence gap。

### 财务诊断

- 财务正文稳定包含五个固定小节。
- 近三年数据按年份完整展示。
- 不出现未提供数字。
- 不出现明显错词、乱码和误译。
- 财务结论能绑定 CodeAct / 结构化财务 evidence。

### 展示

- 九宫格至少展示 6 个有效图表，目标 9 个。
- 二维表金额单位不再显示原始元，而是亿元/万元自适应。
- 指标名称标准化，不出现“鱼子”等错误标签。

### 公告/PDF/网页闭环

- 能从巨潮/交易所/网页资料生成 evidence。
- 财务分析可引用年报经营讨论或公告线索解释指标变化。
- 行业分析可引用研报摘要、行业新闻或主营构成生成行业定位和授信关注点。

## 不做范围

本轮不做：

- 完整 OCR/扫描件 Pipeline。
- 复杂跨页表视觉模型解析。
- Spring Boot 企业后台。
- 全量 LangGraph 原生重构。
- 生产级权限/租户/计费。
