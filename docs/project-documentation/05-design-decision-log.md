# 05 设计决策日志

## 决策 1：创建任务阶段不用 LLM

问题：

- 用户首页输入后，如果创建任务阶段调用 LLM 或外部搜索，会导致页面长时间等待。

决策：

- 创建任务只做本地快速解析。
- LLM 语义能力后移到具体 Agent 阶段。

影响：

- 首页响应速度显著提升。
- 复杂自然语言解析可能不如 LLM 精准，但可以通过规则和已知上市公司映射补足。

## 决策 2：单 Agent 不启动 CrewAI

问题：

- 单个财务分析任务启动 CrewAI 成本高，且容易触发 LiteLLM 限流。

决策：

- 单 Agent 任务走轻量子 Agent。
- 完整尽调才组合多个 Agent。

影响：

- 单任务响应更快。
- CrewAI 从“执行所有事”降级为“综合审查/可选能力”。

## 决策 3：完整尽调先顺序调用四个专项 Agent

问题：

- 直接让 CrewAI 规划和执行完整尽调不稳定，且过程难以调试。

决策：

- 完整尽调 MVP 先顺序调用工商、行业、司法、财务。
- CrewAI 只看四个专项摘要做综合审查，失败则规则生成。

影响：

- 链路更可控。
- Timeline 更清晰。
- 后续可逐步把部分步骤并发化。

## 决策 4：非上市未上传财报不阻塞完整尽调

问题：

- 非上市企业没有财报时，如果直接等待上传，完整尽调体验中断。

决策：

- 引入 `public_pre_dd` 公开资料预尽调。
- 缺失财务指标不计算，报告明确数据边界和待补充材料。

影响：

- 用户可以先得到一份初筛报告。
- 报告不会伪装成正式财务审查。

## 决策 5：财务指标由代码计算，LLM 只写诊断

问题：

- LLM 容易写出错误数值和不通顺财务术语。

决策：

- 三大表解析和指标计算由代码完成。
- LLM 输入只包含已验证指标、RAG 规则和数据边界。
- LLM 输出 JSON，通过质量闸门。

影响：

- 指标可信度提升。
- 文本专业度取决于领域知识和质量闸门。

## 决策 6：行业识别采用规则候选 + LLM 裁判

问题：

- 纯规则容易被经营范围噪声误导，如“进出口”覆盖真实主营。

决策：

- 规则负责召回候选行业。
- LLM 根据企业名、主营、上市公司信息和候选路径做裁判。

影响：

- 士兰微等上市公司行业识别明显改善。
- LLM 失败时仍有规则 fallback。

## 决策 7：RAG 必须可降级

问题：

- embedding 服务、Chroma、网络环境可能失败。

决策：

- 优先向量检索。
- 失败时本地 Markdown 关键词检索。

影响：

- 开发和演示环境更稳。
- 检索质量在 fallback 时下降，但不会导致报告中断。

## 决策 8：Evidence Store 统一证据结构

问题：

- 各 Agent 输出证据格式不一致，报告页难以展示来源和可信度。

决策：

- 使用 Evidence Store 归一化证据。
- 每条证据包含 source、confidence、trust_level、manual_review 等字段。

影响：

- 报告可解释性提升。
- 后续可基于证据做审查追踪和人工复核流程。

## 决策 9：CrewAI 综合审查不直接覆盖正文

问题：

- CrewAI 自由生成可能污染报告，出现不合规或不通顺授信建议。

决策：

- CrewAI 输出作为 advisory。
- 正文由规则报告 builder 生成。

影响：

- 报告稳定性提升。
- CrewAI 的价值需要后续通过严格 schema 和质量闸门释放。

## 决策 10：前端展示 LLM/fallback 来源

问题：

- 用户无法知道报告文本是 LLM 生成还是兜底模板。

决策：

- 财务和行业报告返回 source、provider、elapsed_ms、quality_warnings。
- 前端报告页展示生成方式。

影响：

- 系统透明度提升。
- 用户能理解为什么有些报告更“模板化”。

## 决策 11：不在文档中记录真实 key/token

问题：

- 项目过程中配置过 GitHub、Tavily、Exa、LLM、Embedding 等凭证。

决策：

- 文档只记录配置项和用途，不记录真实值。
- 凭证放在 `.env` 或本机配置中。

影响：

- 降低泄露风险。
- 后续交付时需要单独做凭证轮换和安全检查。

## 决策 12：LangGraph 优先服务私有化交付，SaaS 形态另评估 Dify

问题：

- 当前项目采用 LangGraph 实现编排，但未来可能存在两种商业交付形态：私有化项目和 SaaS 服务。
- 私有化客户通常无法直接访问公网搜索，但可能自购工商、司法、行政处罚等权威数据源。
- SaaS 服务更关注快速搭建工作流、知识库运营、多租户管理和工具配置。

决策：

- 当前 MVP 继续以 LangGraph/FastAPI 自研后端为主，优先适配私有化部署。
- 数据源层保持可插拔，公网搜索只是兜底，不作为正式证据核心依赖。
- 私有化版本重点接客户内网数据源、客户自购 API、内部 RAG 知识库和审计留痕。
- 如果未来以 SaaS 形态提供服务，应单独评估 Dify 化实现，把当前 Agent 逻辑迁移为 Dify workflow、工具和知识库配置。

影响：

- 当前 LangGraph 架构选择是合理的，但它服务的是私有化可控交付，不必强行解释为所有形态的最优解。
- 后续代码要避免把公网搜索写死为核心路径。
- 工商、司法、行政处罚等工具需要设计成本控制和按需调用策略。
- Prompt、RAG 知识、报告模板和 Evidence Store 应保持框架无关，便于未来迁移到 Dify。

## 决策 13：从固定多 Agent 编排演进为 DeepResearch Engine

问题：

- 当前完整尽调是工商、财务、司法、行业四个 Agent 顺序执行，再由报告 builder 汇总。
- 这种方式可以打通 MVP，但缺少研究计划、证据需求、证据缺口和 Claim-Evidence 级别的可审计结构。
- 金融尽调真正关注的是“结论是否有证据、证据是否可信、缺口是否明确”，而不是“Agent 是否调用完成”。

决策：

- 新增 Sequential Thinking 金融尽调 DeepResearch Engine。
- 引擎先生成研究计划，再围绕证据需求调用工具，最后形成 Evidence、Claim、Gap 和 Research Report。
- Sequential Thinking MCP 作为规划和反思能力接入，但第一阶段不强依赖 MCP，可用规则 planner 兜底。
- 现有四个单 Agent 不推翻，作为 research tools 被研究引擎调用。

影响：

- 项目架构从“流程自动化”升级为“研究引擎”。
- Evidence Store 的价值提升为报告可信度核心。
- 前端后续可以展示研究计划、证据链和缺口清单，而不只是时间轴。
- 面试和客户汇报时更容易解释金融 AI 和普通问答机器人的差异。
