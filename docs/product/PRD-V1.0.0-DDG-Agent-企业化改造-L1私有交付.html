一、背景

1.1 业务背景

业务价值：银行对公信贷尽调流程长期面临三大痛点，本产品旨在以 Agent 能力将其压缩到「单一工作台 + AI 辅助决策」。

痛点 现状 成本
数据散在 5+ 系统 工商 / 征信 / 税务 / 流水 / 司法 / 内部 CRM 各自登录 单笔尽调切换系统 30+ 次
报告人工编写 客户经理手写 60+ 页报告 单笔 2-3 天
风险信息滞后 贷后预警靠人工每月翻数据 风险事件平均滞后 30 天发现

用户体验价值点与验证方式：
- 单笔尽调耗时从 3 天压缩到 ≤ 6 小时（任务状态时间戳可验证）
- 报告自动化率 ≥ 80%（报告章节 AI/人工标记可统计）
- 风险预警响应时长 ≤ 1 小时（预警触发到任务状态变化可埋点）
- 客户经理每天 9 点 3 秒内看到「今天必须处理什么」（首页任务分发台）

产品定位：面向银行对公信贷场景的 Agent 能力交付方案。客户银行内部已建有智能体开发平台，核心诉求不是再引入一个平台，而是将财务分析、行业分析等对公尽调能力以 API / SDK 形式集成进现有系统。因此本产品以后端 API 集群为主交付物，前端演示页面用于效果验证。

1.2 为什么用大模型解决

这是 AI 产品 PRD 区别于传统 PRD 的核心问题。尽调场景必须用大模型，而非规则引擎、传统 ML 或纯人工，原因在于其非结构化信息处理 + 多源数据融合 + 推理判断 + 长文报告生成的复合特征。

能力需求 规则引擎 传统 ML 纯人工 大模型
多源非结构化文档（年报/公告/裁判文书/研报）理解 ❌ 无法 🟡 需大量标注 ✅ 慢 ✅ 强
跨数据源的关联推理（财务异常 × 司法风险 × 行业周期） ❌ 固定规则 🟡 单点模型 ✅ 慢 ✅ 强
银行风格尽调报告长文生成 ❌ 模板填充 ❌ 不擅长 ✅ 慢 ✅ 强
证据缺口识别与补充检索决策 ❌ ❌ ✅ ✅

不可替代性：尽调报告的「为什么查这些资料、哪些证据支撑结论、还缺什么材料」这种研究型推理，是规则引擎与传统 ML 无法覆盖的。但数值推理与财务指标计算不交给大模型——由自研 Rebecca 规则引擎完成，从根本上避免幻觉。

ROI 对比：

方案 单笔成本 单笔耗时 覆盖深度
纯人工尽调 1 客户经理 × 3 天 3 天 受精力限制，易遗漏
传统规则系统 低 1 小时 仅结构化指标，无推理
DDG Agent（本产品） LLM Token + 数据源调用 ≤ 6 小时 多源融合 + 可审计推理

1.3 竞品分析

竞品 技术方案 模型选型 核心差异 效果水平
通用 AI 助手（Copilot 类） 单轮/多轮对话 通用大模型 无信贷状态机、无数据源接入、无证据链 不可审计，不适合信贷场景
Dify SaaS 智能体平台 工作流编排 通用大模型 擅长对话入口与轻量编排，难原子化输出财务/行业能力 端到端应用，API/SDK 交付受限
传统尽调系统 规则引擎 + ETL 无 LLM 结构化指标计算强，无推理与长文生成 无 AI 推理，人工补写报告
DDG Agent（本产品） LangGraph Plan-Execute + Rebecca 规则引擎 Qwen3.7 重逻辑 Agent 原子化 API 交付 + 证据链可审计 + HITL + 企业级鉴权可观测 单笔 ≤ 6h，自动化率 ≥ 80%

与 Dify 的关系：非替代，互补。Dify 负责前端对话入口与轻量编排，DDG Agent 负责重逻辑、重数据、重审计的核心尽调能力交付。

1.4 产品目标

业务目标：
- 单笔尽调耗时 ≤ 6 小时（基线 3 天）
- 报告自动化率 ≥ 80%
- 数据引擎健康度 ≥ 95%
- 风险预警响应时长 ≤ 1 小时
- 银行私有化环境一键部署（Docker Compose 隔离环境启动）

模型目标：
- 报告质量评测总分 ≥ 75（通过线）/ ≥ 80（演示线）
- 安全合规维度无违规内容（一票否决）
- 财务分析深度、行业分析深度、正文级引用维度各 ≥ 75
- 单笔尽调端到端延迟（P95）≤ 6 小时（受数据源采集耗时主导，非纯推理延迟）

二、需求描述

2.1 需求清单

以产品功能为粒度。每项是面向银行用户的产品能力，而非研发任务。

序号 优先级 需求点 需求简述（含依赖）
1 P0 尽调任务全生命周期管理 输入企业名创建任务；8 态状态机自动流转；SSE 流式查看执行过程；获取结构化报告。依赖：数据源接入
2 P0 DeepResearch 研究引擎 自动生成研究计划→拆解研究问题→定义证据需求→调用工具→归集证据→生成 Claim→识别证据缺口→合成报告。依赖：专项 Agent
3 P0 财务分析能力 上市公司自动抓取 CNINFO/东财财报；非上市支持 Excel/PDF 上传解析六大表（BS/CF/IS/SCE × 合并/母公司）+ 附注。财报 PDF 多模态解析管道（4 阶段，详见附录 F）—— ① 拍照成字：MinerU API/SDK（mineru.net，每日 1000 页免费）解析 PDF → 带坐标和类型的 content_list JSON；② 蚂蚁抄数：MiniCPM-V-4.6-Instruct API（api.modelbest.co，OpenAI 兼容 + 免费公钥）逐表转录数值，只抄不算；③ 代码算账：23 条+ 会计恒等式确定性引擎逐条勾稽，红黄绿分级，高自动判定率（目标 ≥85% 勾稽发现自动解决，仅 OCR 级错误上浮人工）；④ 看图兜底：跨页/宽表/图表走 qwen3.7 视觉，过勾稽才采信。汇总后喂入 Rebecca 规则引擎计算财务指标（不依赖 LLM 数值推理）。POC 验证：同技术栈 demo（ocr.quaesto.com，详见 §15.1）实测三木集团年报，MiniCPM-V-4.6 抽取 560 数字、467 勾稽通过、7/8 自动判定。依赖：财报数据源 + MinerU + MiniCPM-V-4.6 + 勾稽规则引擎
4 P0 行业分析能力 基于行业分类 + 本地 RAG 知识库；向量+BM25 混合召回 + RRF 融合 + Rerank 精排；输出景气度/格局/政策/授信关注点。依赖：知识库
5 P0 工商与司法分析能力 通过元典 MCP/权威通道核查工商登记、股权、裁判、执行、处罚；搜索兜底。依赖：外部数据通道
6 P0 8 章结构化授信报告 稳定输出 8 章贷前尽调报告；每条结论绑定 evidence_refs；附证据链与待补充材料。依赖：DeepResearch 引擎
7 P0 可审计证据链 每条论断附来源、引用、可信度评级；报告页「查看证据」一键跳转原始证据。依赖：Evidence Store
8 P0 HITL 人工在环 主体确认/计划确认/财报上传/证据缺口节点可中断，等待人工输入后恢复。勾稽核验 HITL：三处联动核对——左侧原始 PDF（按勾稽结果高亮着色：绿=通过/红=疑似OCR错/灰=未参与/黄=暂不定）、右上核验队列（逐条偏差金额+规则代码）、右下结构化报表（完整科目对照）；导出三件套（干净报表/底稿/审计轨）。布局参考 §15.1 ocr.quaesto.com 工作台。依赖：LangGraph 原生 HITL
9 P0 报告质量门 报告生成前过综合质量门（业务报告质量 9 维 100 分 × 0.9 ＋ RAG 检索质量 RAGAS × 0.1）；证据不足自动补充研究；RAG 检索质量低于阈值回退重做。依赖：报告组装
10 P0 财报上传与解析 支持 Excel/CSV/PDF 上传；PDF 到达后走 MinerU OCR → MiniCPM-V 抄数 → 23 条恒等式勾稽 → 视觉兜底 四阶段管道；解析返回标准化三大表数据（含红黄绿校验标记）。依赖：财务 Agent + MinerU + MiniCPM-V + 勾稽规则引擎
11 P0 JWT 认证与权限 登录获取 Token；未登录访问 API 返回 401；任务数据按用户隔离。依赖：用户体系
12 P0 任务持久化与恢复 任务状态写入 PostgreSQL；服务重启后进行中任务可恢复。依赖：PostgreSQL + Alembic
13 P1 API 限流 slowapi 按路由限流；单 IP 超限返回 429，防滥用。依赖：JWT
14 P1 全链路可观测 Langfuse 追踪 LLM 调用；Prometheus+Grafana 监控；结构化日志带 request/session/user 上下文。依赖：API 层
15 P1 记忆双轨 SQLite+FTS5 短期/长期记忆保留；pgvector 语义检索可选；统一入口业务无感知。依赖：核心引擎
16 P1 批量尽调定时任务 每日 02:00 自动批量尽调存量客户；写入批量任务日志表。依赖：任务接口
17 P1 前端登录鉴权与 API 分层 登录页 + 鉴权状态管理 + token 拦截 + 路由守卫 + 401 处理；现有 UI 零改动。依赖：JWT
18 P1 风险问答（AG-UI） 审批人对报告疑点发问，AI 基于报告+数据源流式回答，必须带引用，置信度<70% 提示人工确认。依赖：报告 + Evidence

性能需求：

指标 标准 说明
首 Token 延迟 ≤ 3 秒 SSE 首个事件（计划生成后）
端到端延迟(P95) ≤ 6 小时 单笔尽调完整周期，受数据源采集主导
并发支持 ≥ 5 个并发尽调任务 峰值并发量（单进程足够，无需 Worker 架构）
可用性 ≥ 99.5% 月度服务可用性（私有化环境）
报告生成（纯推理） ≤ 30 分钟 analyzing 阶段 AI 生成报告耗时

安全需求：
- 数据不出境：银行私有化部署，LLM 走银行内网 qwen3.7 服务，天然满足
- JWT 认证：未登录访问 /api/v1/tasks 返回 401
- 限流：单 IP 超过阈值返回 429
- 数据加密：PostgreSQL 存储任务数据，访问控制基于 JWT
- 不对接央行征信直连（合规要求，必须经银行内部中台）
- 不替代审批人最终决策（监管要求 + 信任问题）

数据需求：
- 埋点数据：任务状态时间戳、工具调用 trace、LLM 调用（Langfuse）、API 请求（Prometheus）
- 正负 Case 数据：报告 JSON 自动落盘到 backend/output/reports/，回归样例 10 家上市公司
- 业务数据：尽调任务、证据、Claim、报告章节、批量任务日志

AI 节点标注：
- LLM 调用节点（qwen3.7）：研究计划生成、研究问题拆解、Claim 生成、报告章节合成。预期单次延迟 3-15 秒。
- 工具调用节点：财务（Rebecca 规则引擎 + akshare + pdfplumber）、行业（ChromaDB RAG + SearXNG）、工商/司法（元典 Yuandian MCP）。
- 判断/路由节点：Intent Extractor 任务类型分类决定走完整尽调还是专项；证据缺口判断决定是否补充检索。
- 人工介入节点：计划确认、主体确认、财报上传、证据缺口补充。
- 异常处理分支：数据源超时 → 标注「数据不完整，结论可信度降低」；LLM 失败 → 重试；质量门不通过 → 回退补充研究；服务重启 → 从 PostgreSQL 恢复任务。

架构参考：本流程的 Plan-Execute-Gap-Report 循环与开源项目 GPT Researcher（§15.2） 的 Planner-Executor-Publisher 模式理念一致；可在证据缺口补充阶段借鉴其递归树状 Deep Research（breadth/depth）对多分支线索并行探索，在报告合成阶段借鉴其 Reviewer/Reviser 章节级质检子图，降低整体质量门回退率。

五、模型选型

核心原则：从小参数模型开始验证，效果相似时优先使用小参数模型（成本低）。本场景已锁定主模型，选型结论以验证为准。

5.1 选型约束条件

约束维度 要求 说明
推理成本预算 ≤ 0.05 元/千次输入 Token 私有化场景成本敏感
延迟要求 单次 LLM 调用 ≤ 15 秒 不阻塞 SSE 流式体验

数据合规 数据不出境 银行场景硬性要求

5.3 选型结论

  • 最终选择：Qwen3.7（阿里云百炼，OpenAI 兼容接口）。理由：① 银行内网已具备 qwen3.7 服务，零额外部署成本；② 中文金融场景效果优秀；③ OpenAI 兼容接口，与 LangChain/LangGraph 生态无缝；④ 数据不出境天然满足。
  • 备用模型：暂不启用 Failover。当前并发峰值仅 ~5，qwen3.7 服务稳定；产品内置 LLM 循环降级能力保留备用，待出现稳定性需求再启用（可降级到 DeepSeek-V3）。
  • 成本预估：单笔尽调约 8-15 次 LLM 调用，单笔 Token 成本约 0.5-2 元；峰值 5 并发 × 日均 20 笔 ≈ 日均 30-60 元。

关键设计决策：财务指标的数值推理与计算不交给 LLM，由自研 Rebecca 规则引擎完成，从根本上避免数值幻觉。

六、Prompt 工程设计

Prompt 是核心交付物，必须文档化管理。DDG 采用多 Agent 架构，每个专项 Agent 有独立 System Prompt。

6.1 System Prompt 设计

角色定义与能力边界：

Agent 角色 能力边界
Research Planner 金融尽调研究规划师 拆解尽调目标为研究问题与证据需求，不直接下风险结论
Financial Agent 银行风格财务分析师 基于 Rebecca 引擎输出的结构化指标做诊断，不做数值计算
Industry Agent 行业研究分析师 基于 RAG 知识库输出行业研判，不编造未检索到的政策
Commerce Agent 工商核查专员 基于权威工商数据核查主体信息
Judicial Agent 司法合规审查员 基于司法/处罚数据识别风险，不臆测未命中记录
Report Synthesizer 授信报告撰写人 装配 8 章报告，每条结论绑定 evidence_refs

角色设计参考：上述 Agent 划分与 GPT Researcher（§15.2） 的 Editor/Researcher/Writer 多 Agent 协作理念一致。后续可在报告合成阶段引入 Section Reviewer 与 Section Reviser 两个新角色：Reviewer 按银行授信 9 维评分标准逐章评审，Reviser 根据评审意见修改，形成章节级质检循环。

输出约束：
- 结构化 JSON 输出（Claim、Evidence、报告章节均有 schema）
- 每条结论必须附带 evidence_ids，无证据不下结论
- 禁止输出「暂不可用」「暂不可计算」「mock」「兜底模拟」等占位表达
- 语言风格：银行授信报告体，专业、克制、可审计

核心指令（Research Planner System Prompt 示例）：

你是一名银行对公信贷尽调研究规划师。你的任务是将客户的尽调目标拆解为结构化研究计划。

## 能力边界
- 你只负责规划研究问题与证据需求，不直接给出风险结论。
- 你不进行数值计算（由 Rebecca 规则引擎完成）。

## 输出格式（严格 JSON）
{
  "objective": "本次尽调目标",
  "tasks": [
    {
      "task": "研究问题描述",
      "evidence_required": ["所需证据类型"],
      "priority": "high|medium|low"
    }
  ]
}

## 规则
1. 完整尽调必须覆盖：主体确认、财务趋势与偿债能力、司法/处罚/担保风险、行业周期与竞争格局、授信安全边界。
2. 每个研究问题必须明确所需证据类型（如：近三年三大表、诉讼公告、行业研报）。
3. 不得编造企业信息，缺失信息标记为证据缺口。
4. 禁止输出占位表达（暂不可用、mock 等）。

6.2 Prompt 策略

策略 是否采用 说明
Few-shot 示例 是 研究规划、报告合成采用少量高质量示例（2-3 个），按企业类型动态选取
Chain-of-Thought 是 Claim 生成要求展示「现象 → 归因 → 风险定性」推理链（产品化为可审计研究步骤，非模型私密思维链）

八、评测体系

评测集是 AI 产品最核心资产之一。DDG 采用「业务报告质量（9 维度 100 分）+ RAG 检索质量（RAGAS 技术轨道，10% 权重）」双轨评测体系，综合质量门按 9:1 合并计算。

8.1 评测集构建方法论

数据来源：
- PM 人工构造（MVP 冷启动）
- 10 家上市公司真实尽调报告采样（士兰微/卓胜微/闻泰科技/欣旺达/川能动力/蓝思科技/药明康德/阳光电源/牧原股份/航发动力）
- 线上 Bad Case 回流

覆盖度设计：
- 核心场景（70%）：上市公司完整贷前尽调主路径
- 边界场景（20%）：非上市公司财报上传、数据源缺失、简称识别
- 对抗场景（5%）：Prompt 注入、企业名混入任务话术（如「分析一下欣旺达」）
- 安全场景（5%）：违规/敏感内容输入

8.2 评测维度与评分标准

维度 权重 1 分（差） 3 分（及格） 5 分（优秀）
主体识别 10% 混入任务话术 基本正确 精准识别主体与证券代码
报告结构 10% 章节缺失 基本 8 章 稳定输出 8 章贷前结构
证据深度 15% 无证据 evidence 偏少 ≥16 项含 ≥4 高可信 ≥4 source_url
正文级引用 15% 无引用 部分引用 ≥5 非附录章节含正文级引用
财务分析深度 15% 无趋势 仅单年指标 近三年趋势 + 异常归因 + 诊断
行业分析深度 15% 通用话术 基本覆盖 细分定位+周期+格局+政策+上下游+授信关注
工商/司法覆盖 8% 严重遗漏 基本覆盖 工商+股权+裁判+执行+处罚全覆盖
授信建议一致性 7% 病句/矛盾 基本一致 分数/等级/额度/期限/担保全一致
语言质量 5% 病句/占位 基本通顺 专业银行体

评分机制：综合质量门由两条轨道合并计算——

综合质量分 = 业务报告质量（满分 100）× 0.9 ＋ RAG 检索质量（满分 100）× 0.1

其中「业务报告质量」为上方 9 维度加权求和（满分 100）；「RAG 检索质量」为下方 §8.2.1 的 RAGAS 技术轨道（满分 100）。两者相互独立：业务分衡量「报告写得好不好」，技术分衡量「RAG 管道健康不健康」，前者依赖后者但不可互相替代。

安全合规为一票否决项（出现违规内容直接不通过）。

通过标准：
- MVP 上线：综合质量分 ≥ 75，业务报告质量 ≥ 75，无 P0，P1 ≤ 3
- 演示标准：综合质量分 ≥ 80，业务报告质量 ≥ 80，财务分析深度 ≥ 75，行业分析深度 ≥ 75，正文级引用 ≥ 80，RAG 检索质量 ≥ 75

8.2.1 RAG 检索质量（技术轨道，权重 10%）

借鉴多模态 RAG 风电运维项目的 RAGAS 评测实践。DDG 原有 9 维评分聚焦「报告产出质量」，缺少对检索链路本身的客观度量——召回的上下文是否精准、是否充分、是否被忠实使用。引入 RAGAS 作为独立技术轨道，在每次评测集跑批时自动计算，既作为质量门的 10% 权重项，也作为 RAG 管道（向量 + BM25 + RRF + Rerank 参数）调优的回归基线。

RAGAS 指标 含义 目标 说明
ContextPrecision 召回上下文的精准度（相关 chunk 是否排在前） ≥ 0.75 衡量 Rerank 精排与 RRF 融合效果
ContextRecall 召回上下文的覆盖率（应召回的是否都召回） ≥ 0.75 衡量向量 + BM25 混合召回的召回率
Faithfulness 回答对召回上下文的忠实度（是否幻觉） ≥ 0.90 衡量 LLM 是否脱离证据编造
ResponseRelevancy 回答与问题的相关度 ≥ 0.85 衡量最终论断是否命中尽调要点

计算方式：在评测集上以 Golden Context / Golden Answer 为基准，由 RAGAS 框架自动打分（无需人工标注，可纳入 CI 回归）。L1 私有交付阶段以离线批跑为主（每日 02:00 Cron 跑批后触发），L2 规划线上实时采样评测。

与业务维度的关系：
- ContextRecall / ContextPrecision 偏低 → 直接拖累「证据深度」「正文级引用」「行业分析深度」
- Faithfulness 偏低 → 直接触发「安全合规一票否决」的幻觉风险
- 技术分低于阈值（< 70）→ 即便业务分达标也回退，防止「报告写得好但检索不可信」的虚假通过

8.3 评测集示例

正向（单笔完整尽调）：
- 输入：企业名「士兰微」
- 期望输出：8 章报告，主体识别为半导体 IDM，近三年财务趋势，行业定位准确，≥16 evidence，每条结论绑定 evidence_refs

负向（对抗场景）：
- 输入：「分析一下欣旺达的财务风险情况」
- 不期望输出：主体识别为「分析一下欣旺达」（P0）

8.4 评测执行流程

评测方式：
- 规则评测器自动评测（report_quality_evaluator.py，底线质量门）
- LLM-as-Judge 二级评审（规则评测通过后，对诊断深度做语义评审）
- 离线批量回归（run_report_quality_regression.py，跑 10 家公司生成 Markdown 总结）
- 章节级 Reviewer/Reviser 内循环评测（报告生成过程中逐章自检，参考 §15.2 GPT Researcher 的子图质检模式）

触发条件：Prompt 变更、模型版本升级、线上 Bad Case 累计、周期性回归（每次迭代）。

达标标准：
- 灰度发布：总分 ≥ 75，安全合规无违规
- 全量上线：总分 ≥ 80，财务/行业/引用维度各 ≥ 75

8.5 财报解析管道效率指标

与 §8.2 的业务报告质量和 RAG 检索质量不同，本组指标衡量财务 PDF 解析管道本身的效率和可信度——数字被正确提取了多少、自动化处理了多少、哪些规则族未覆盖。这四个指标直接来源于同技术栈 POC demo（ocr.quaesto.com，详见 §15.1，MiniCPM-V-4.6 + 确定性引擎）的验证实践。

指标 含义 目标 计算方式
数字触达率 年报 PDF 中可被管道提取并参与勾稽的数字占比 ≥ 80% 勾稽通过数 / PDF 实际数字数
自动判定率 所有勾稽发现中被确定性引擎自动解决（无需人工复核）的比例 ≥ 85% 自动判定条数 / 总勾稽发现条数
主表覆盖率 六大表（BS/CF/IS/SCE × 合并/母公司）的覆盖完整度 6/6 已解析主表数 / 6
规则族覆盖率 勾稽规则中已实施的规则族占比 目标全覆盖 已实施规则族数 / 总规则族数

POC 基线（三木集团 2024 年报，MiniCPM-V-4.6 + 确定性引擎）：数字触达 85.2%，抽取 560 数字，467 勾稽通过，8 条发现中 7 条自动判定。

与质量门的关系：数字触达率 < 80% 或自动判定率 < 85% 时，财报解析章节自动标记「置信度不足」，收入 Evidence Store 时标注低可信度，授信建议中使用该数据处提示审慎。

8.6 评测集持续维护

  • Bad Case 回流：报告 JSON 自动落盘 backend/output/reports/，定期纳入回归
  • 场景扩展：新增行业（如军工、医药）同步增样例
  • 版本管理：每次回归输出 summary.json + summary.md，可接 CI
  • 定期清理：剔除过时样例，保持评测集与业务同步

- 结果不确定性：报告章节支持「重新生成」「局部重写」
- 用户反馈入口：风险等级人工调整（带 ≥30 字理由）、结构化退回意见
- 异常状态引导：数据源超时标注「数据不完整，结论可信度降低」；置信度 < 70% 提示「建议人工确认」
- 人工介入入口：计划确认、主体确认、财报上传、证据缺口补充（HITL 中断恢复）
- 证据追溯：报告每条结论「查看证据」一键跳转原始证据

十一、AI 能力边界说明

能做到：
- 上市公司完整贷前尽调（10 家回归样例验证：半导体/新能源/电子制造/医药/农业/军工）
- 非上市公司财报上传解析（Excel/PDF 三大表）+ Rebecca 规则引擎财务诊断
- 多源数据融合（工商/司法/财务/行业）+ 可审计证据链
- 8 章结构化授信报告生成，每条结论绑定证据
- HITL 在关键节点中断恢复
- 每日 02:00 批量尽调存量客户
- 私有化部署，数据不出境

做不到：
- 不对接央行征信直连（合规要求，经银行内部中台）
- 不替代审批人最终决策（监管要求）
- 不做实时行情/高频交易分析
- 不支持多语言（当前仅中文）
- 非上市公司无公开数据时，财务分析依赖人工上传财报

已知缺陷（当前版本不修复）：
- 部分长尾行业知识库覆盖不足，行业诊断可能偏通用
- 简称识别偶有偏差（如「蓝思科技」需精确匹配）
- 私有化环境无外网时，pgvector embedding 需配置本地 embedding 服务（当前双轨默认走 SQLite+FTS5）

15.1 财报解析与勾稽核验工作台（ocr.quaesto.com/demo）

15.1.1 项目概述

一个基于 Gradio 构建的财报 PDF 解析与人工勾稽核验演示工作台，核心流程为：

  1. 选样本 / 上传财报 PDF；
  2. 查看核验队列中的疑似 OCR 错误；
  3. 逐条三处联动核对原文并裁决/修正；
  4. 导出核验成果（干净报表 / 底稿 / 审计轨）。

15.1.2 对 DDG 的启发

启发点 DDG 应用方式
四阶段管道可行性验证 MinerU 解析 → MiniCPM-V-4.6 转录 → 会计恒等式勾稽 → qwen3.7 视觉兜底，与附录 F 设计完全一致
POC 指标基线 三木集团 2024 年报：560 数字、467 勾稽通过、7/8 自动判定，数字触达率 85.2%，作为 DDG 财报解析效率指标基线
HITL 三处联动界面 左侧 PDF 原文（绿/红/黄/灰着色）+ 右上核验队列（偏差金额 + 规则代码）+ 右下结构化报表，直接作为 DDG 勾稽核验 HITL 页面布局参考
导出物设计 干净报表、底稿、审计轨三件套进入 DDG Evidence Store，作为授信报告证据链组成部分
跨页/宽表处理 演示中表格按页懒加载（如 table t837 pages 68,69,70,71），提示 DDG 需处理年报中跨页、宽表、图表等特殊版面

15.1.3 使用边界

  • Demo 为 Gradio 原型，生产前端需按 DDG 技术栈重写；
  • MinerU 为 SaaS API，私有化无外网时需评估本地部署或 PaddleOCR 离线替代方案；
  • MiniCPM-V-4.6 免费公钥有频率限制，L1 交付需确认商业授权或本地部署。

15.2 GPT Researcher（assafelovic/gpt-researcher）

15.2.1 项目概述

一个 28K+ stars 的开源自主研究 Agent，支持 Plan-Execute-Publish 三段式、LangGraph 多 Agent 协作以及递归树状 Deep Research。其核心 LangGraph 流程为：

Browser → Editor → Researcher → Reviewer → Reviser → Writer → Publisher

其中 Reviewer/Reviser 构成章节级质检循环，Deep Research 模式通过可配置的 breadth 和 depth 对子主题递归探索。

15.2.2 对 DDG 的启发

启发点 DDG 应用方式
章节级 Reviewer/Reviser 子图 DDG 当前为报告生成后整体质量门，可引入每章生成后的 Reviewer 评审 + Reviser 修改循环，降低整体回退率
递归深度研究 在证据缺口补充阶段，将线性 follow-up 升级为树状探索（如司法风险同时分支查询裁判、执行、处罚、监管问询），但 depth 建议 ≤2，避免公开搜索噪声
成本分层 小模型/规则负责 query 生成、证据摘要；qwen3.7 仅用于计划、Claim、报告合成等关键节点，降低单笔尽调成本
Publisher Agent 参考其 PDF/DOCX/Markdown 导出能力，为 DDG 增加授信报告可下载交付物
子图隔离 将 Planner、Task、Section、Quality Gate 拆分为独立 LangGraph 子图，提升可维护性和可测试性

15.2.3 使用边界

  • GPT Researcher 面向开放网络研究，DDG 必须以权威工商/司法/财报数据源为主，公开搜索仅作线索；
  • 其报告结构通用，DDG 必须固定 8 章授信结构和证据链格式；
  • Reviewer guideline 需替换为银行授信报告 9 维评分标准，不可复用通用标准。

F.3 MiniCPM-V-4.6（阶段② 蚂蚁抄数）

项目 详情
模型全称 MiniCPM-V-4.6-Instruct（1.3B 参数，AWQ W4A16 量化）

「只抄不算」Prompt 设计原则：每次 API 调用传入单个表格图片 + system prompt 约束「逐字转录表格中的每个数值，不执行任何计算、不推断、不补全缺失数据」。转录结果直接输出为结构化 JSON（行×列网格），后续由阶段③勾稽引擎校验。

F.4 为何不用 PaddleOCR

维度 PaddleOCR 当前方案（MinerU）
SaaS API ❌ 无独立 REST API（仅 Web UI） ✅ 完整 REST API + Python SDK
程序化集成 需本地部署 PaddleServing + GPU 直接 HTTP 调用，无需自建服务
版面分析 PP-Structure 支持，但需本地部署 MinerU content_list 已内置分类 + 坐标
输出格式 需自行拼装 Markdown + JSON 直接可用
维护成本 需维护 GPU 服务器 + 模型更新 零运维，SaaS 按量使用

结论：PaddleOCR 在本地部署场景下是优秀方案，但对于 L1 私有化交付来说，MinerU 的 SaaS API 模式匹配度更高——无需额外 GPU、无需维护 OCR 服务，且输出格式与管道后续阶段直接对接。L2 如需完全离线部署，可将 MinerU 替换为本地 PaddleOCR + PP-Structure 做等价替代。
